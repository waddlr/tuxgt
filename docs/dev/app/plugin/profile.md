# Profiles

One active profile per game. The live `games/<rel>/` tree is that profile. Inactive roots are parked slots. Play reads the live tree after a finished switch. The profile menu switches, creates, renames, and deletes. It does not launch.

Adapter and Launch Mode stay on the game. A switch that disarms Launch Mode remembers the arm in `launch-memory.toml` beside `apply.toml` (also on the game, never parked), and a later switch to a profile that needs a channel re-arms it (see Switch). `apply.toml`, `backups/`, and `game_args_published` stay on the game. `tux-protonfixes.conf` is regenerated by `sync_session`. It is not swapped as a blob.

## Owned bytes

Manifests, stage, runtime, `disabled/`, `tuxgt-launcher.ini`, per-game knobs, custom env, wrappers, and the launch-argument working copy (`game_args`, `game_args_custom`). That working copy is parked in the slot's `knobs.toml`. Globals are not per-profile. `game_args_published` stays on the game.

`profiles/<id>/profile.toml` is `id`, `name`, and `kind` only. No parent and no resolved snapshot. A later link stores a delta and re-resolves its one parent on activate. Parking a link writes the delta. Copy of a link flattens. One level. No write-through. No Make independent.

## Kinds

| Id | Kind | Name |
|---|---|---|
| `unmodded` | unmodded | Unmodded |
| `default` | default | Default |
| `pN` | user | chosen |

Names are unique per game, case-insensitive. The display name Unmodded is reserved. Unmodded cannot be renamed or deleted. Default cannot be deleted.

First open with no `profiles.toml` writes Unmodded and Default. Any instance (including a disabled one), knob, custom env, wrapper, launch-argument row (including a disabled one), or non-empty custom arguments makes Default active and leaves the live files in place, with no Default slot yet. An empty game stays on Unmodded and writes an empty Default slot. A second open does not move files.

Empty means no manifests, no knobs, custom env, or wrappers, and no launch-argument rows or non-empty custom arguments. A parked ini or runtime does not make Default non-empty. When Default is not active, emptiness is the slot, not live sqlite.

## Copy and empty

A new profile can start empty, or as a copy. The dialog opens on Copy. Empty hides the base picker. Copy of the active profile reads the live tree. Never clone an empty slot for the active profile. Create and use makes the new profile active. CLI `profile add` does not switch.

## First edit while Unmodded is active

The edit moves to Default before it is written.

- Default empty: switch with no confirm. The GUI toasts “Saved to Default.”
- Default already has changes: `Error::NeedProfile` with `Add this to Default?`, and nothing is written. The caller confirms, calls `activate_default_for_write`, and retries. The retry is a no-op gate.

This is not `Error::NeedConfirm` and not install’s `yes`. Those loops retry with `yes=true` and would swallow the consent. Add-to-Default always prompts, including when the command has `--yes`. It does not set the foreign-confirm `yes`. Without a terminal it errors and writes nothing, and the error does not suggest `--yes`.

Not redirected: `set_steam_appid`, extra exe, doctor overrides, game handle, `convert_game_adapter`, global knobs, `push_global_edits` when the game has no instances. `place_instance_slot` is not gated.

## Switch

A preview names install-adapter dests whose presence or sha differs (later `load_order` wins), whether the switch drops the last channel need while an Apply record exists, and whether completing it will write store launch options (an Apply restore or a remembered Apply re-arm). Missing slot means empty. Unmodded is not special-cased as empty. The incoming tree is the slot, unless the target is already active.

Confirms happen before any write and before the journal exists. Three phases when all apply. Files first (`Error::NeedConfirm`, prefix `profile-files:`), then Apply restore (`profile-restore: Update Launch Options will be restored.`), then store-client stop (`profile-client-stop:`) when a predicted store launch-options write would happen while the owning client is running. A refused confirm writes nothing. `--yes` accepts all. A prompted accept sets only that phase.

The core switch does not stop the store client. Explicit GUI and CLI switch flows collect the client-stop consent after the file/restore confirms, stop the client, run the switch, and restart the client; denying it leaves the active profile, files, Apply record, and Launch Mode untouched. With the client stopped, `sync_session` restores or re-applies inside the switch. `restore_deferred` and `rearm_deferred` remain only as race/resume fallbacks (the client starts after the gate, or a journal resumes), finished by the CLI or GUI through the existing client-stop flow.

Launch Mode memory: the switch captures the armed channel (Hook handle first, else an Apply record) into its journal before parking. After the incoming profile is live and `sync_session` has run: if the incoming profile needs no channel and an arm was captured, that arm overwrites `launch-memory.toml` (a switch between two need-free profiles captures nothing and keeps any earlier memory). If the incoming profile needs a channel and an arm is already active, any memory is stale and is cleared. If none is active and a memory exists, it re-arms: Hook only when structurally legal for the incoming needs (no args, no argv wrappers, not install-only; Proton flavor is not re-checked — the arm was the user's on this game), Update Launch Options by re-applying inside the switch when the store client is not running, else `rearm_deferred` as the race/resume fallback above. Memory clears only on a successful re-arm; an illegal remembered arm stays remembered for a later profile. The memory is switch-scoped: disarms outside a switch (last mod uninstalled, last knob cleared) never write it, and needs appearing outside a switch never consume it.

TuxGT has no game-process probe. `StoreClient::running()` is Steam or Heroic, not the game. A file-changing switch still confirms. It does not stop the store, and it is not refused because Steam is running.

Journal `profile-switch.toml` phases: `parking`, `parked`, `removed`, `cleared`, `loaded`, `installed`. The journal is written before any mutation. A later open resumes it to completion with the stored yes flags and does not ask again. Resume of `parking` wipes the partial slot and parks again from live. Outgoing enabled install-adapter dests are removed winners first. Live manifests, stage, runtime, `disabled/`, and the ini are cleared. `profiles/`, `profiles.toml`, the journal, `apply.toml`, `backups/`, and the conf stay. The incoming slot is loaded (a missing slot leaves live empty and clears sqlite knobs, custom env, wrappers, and the launch-argument working copy). `game_args_published` is not cleared. Active is set. Enabled install manifests are copied. `prewire_game` then `sync_session` (`PluginHost::load()`). The journal is deleted.

Deleting the active user profile switches to Default first (same confirms), then deletes the slot. CLI `profile remove` can remove an inactive slot directly. The GUI Delete acts on the active profile only.

## GUI

The hero shows one display-only pill, `Profile: <name>`, in its own row under Play and above the chips. It does not select. The chip row is unchanged, including the Unmodified pill. Selection lives in the Profile card on General (Column 2 Row 1): title, one muted line (“A profile is a saved set of mods and settings for this game.”), then a Current dropdown. While profiles have not loaded, the pill reads `Profile: …` and the dropdown is disabled.

The menu lists profile names, with the active one checked, then New profile…, Rename… (absent on Unmodded), and Delete (absent on Unmodded and Default). No Linked row. No History. No next-launch line. No play-once.

The profile dialogs (New, Rename, Delete, file-changes, and Apply-restore confirms) are app-owned modals in the client-stop card's style: full-window dim, card centered on both axes, click-outside or Escape cancels. Add-to-Default is a card on the game page, not a dialog and not `ConfirmOp`. Cancel drops the card and the install and uninstall queues. A successful switch toasts “Using {name}.” and reloads mods, knobs, env, and the Apply arm. A deferred restore uses the existing client-stop card, then `restore_launch`. It does not unhook.

## CLI

`tuxgt profile list <game>` prints `name` then a tab, and `active` on the active row. `use <game> <name> [--yes]`. `add <game> --name <name>` (empty) or `--from <name> --copy` (the two flags together; no `--link`). `rename <game> <name> <new>`. `remove <game> <name> [--yes]`. Non-interactive use and remove without `--yes` error and write nothing. There is no `tuxgt launch --profile`.

## Later

These are specified and not built. `profile.link`, `profile.history`, and `profile.once` stay Missing until their own tasks.

History keeps 25 entries of owned staged files whose live bytes differ from the depot sha, because the config editor writes in place and does not update `staged_sha`. Go-back proves the blobs exist before it writes. The confirm names the discarded changes and says they cannot be brought back. A link’s last line says the parent is not changed. If game-dir or prefix files would change, the confirm says those files are put back too, with no paths.

Next launch is a CLI pointer only. The hook’s `inject!=1` early return must not delete it. It is refused when game-dir or prefix files would have to change.
