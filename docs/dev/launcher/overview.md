# Launcher

C preload. Source: `src/launcher/*.c`, `src/launcher/tuxgt-launcher`. Build: `make preload`.

Goal: stage versioned injector trees from a central depot into `GamesDir/<exe>/` and `LoadLibraryW` them in ini order, without copying anything next to the game exe. Two preloads: `build/libtuxgt-launcher.so` (64-bit) and `build/libtuxgt-launcher32.so` (`gcc -m32`). Selection/payload/staging plumbing for DirectX 9/10/11/12 (including 32-bit) is supported. The `-m32` SO has an i386 gate (`launch.32bit-in-game-gate` Exists). In-game DX9/DX10 proof is verified. The loader is injector-agnostic: no injector names or kinds in keys or code, only `LoadDLL` (staged, then loaded) and `IncludeFile` (staged only).

## References

- `external/reshade/ReShade64.dll`: stock 6.8.0.2155, `ReShadeRegisterAddon` export. `ReShade32.dll` + Vulkan/XR jsons out of scope.
- `external/dlss5-bridge-main/`: addon source v1.3.0 reference. `external/renodx-dlss.addon64`: addon binary reference.
- `external/*.dll` (`ReShade`, `nvngx_*`): runtime payloads, never committed, user-supplied.
- ReShade base path (`dll_main.cpp:get_base_path`): `INSTALL BasePath` in the DLL-named global config (e.g. `ReShade64.ini`) wins, else `RESHADE_BASE_PATH_OVERRIDE` env wins, else DLL-dir/exe-dir default. Log path = config path with `.log` extension.

## Design

- Preload (`src/launcher/*.c`, pure C): builds `libtuxgt-launcher.so` (64-bit) and `libtuxgt-launcher32.so` (`gcc -m32` when available); constructor only `dlsym(poll/ppoll)`; `poll/ppoll` → wine filter → arm 5-byte `E9` gates on `LoadLibraryW/ExW/Sleep/SleepEx/GetTickCount/QPC` once `kernel32` is mapped; first gate hit on a PE thread runs `LoadLibraryW` of the resolved DLL. Never `LoadLibraryW` from a Unix `poll` stack. Opt-in: exe stem needs its own ini section.
- PE export resolve: follows `MODULE.Export` directory forwarders and `E9`/`FF 25` thunks. `MODULE.#ordinal` is not parsed — proton-cachyos x64 `kernel32`/`kernelbase` have none (101/96 named forwarders, 0 `#N`); the hooked APIs are named thunks into kernelbase, not export-directory strings. A `#ordinal` miss returns NULL (that gate skipped / `no-loader`), not a jump into the ASCII forwarder.
- Env visibility rule: Unix `setenv` is NOT visible to PE `GetEnvironmentVariableW` (PEB snapshot), so anything a loaded DLL must see goes through the PE side too: the loader sets it via kernel32 `SetEnvironmentVariableW` from the PE thread before loading. Instance: `RESHADE_BASE_PATH_OVERRIDE` in the stock-name quirk below.
- Loading check / base-path quirk (reshade-main `dll_main.cpp:64–71,129-156`), triggered by LoadDLL dest basename, never by config keys: a dest named `ReShade64.dll`/`ReShade32.dll` (case-insensitive) touches a minimal `<base>/ReShade.ini` when missing (the stock-stem loading check refuses `LoadLibrary` without it) and sets `RESHADE_BASE_PATH_OVERRIDE` (Unix + PE) at the per-game base. Proxy-named loads (e.g. `d3d12.dll=ReShade/6.8.0.2155/ReShade64.dll`) need neither: the DLL dir already is the base and the stock-stem check does not apply. Game-dir `ReShade.ini` `[INSTALL] BasePath` still wins over the override (stock `get_base_path` order) — accepted.
- ReShade dest MUST be stock-named. A `LoadLibraryW` of a proxy-named ReShade (dest `dxgi.dll`) does not install DXGI hooks, because ReShade defers when the hook target filename matches its own (`register_export_module` → `hook::call` → `ensure_export_module_loaded` in reshade-main `source/hook_manager.cpp`). That design assumes the classic install where the game imports the proxy; loaded by bare `LoadLibraryW` with nothing importing it, the call never comes. The stock basename does not match a hook target, so every API hooks immediately. Same caution for any injector with call-triggered hooks: proxy slots need per-slot in-game proof, never assume.
- No `Type`→DLL mapping, no `[Binaries]`, no `Reshade` key, no `TUXGT_VERSIONS`/`TUXGT_RESHADE`. `Type` (`dx9_64`/`dx10_64`/`dx11_64`/`dx12_64`/`dx9_32`/`dx10_32`/`dx11_32`/`dx12_32`, `[Defaults]` seed) is parsed and reported in the status file only. Every DLL to load is an explicit `LoadDLL` entry; depot paths are explicit (`ReShade/6.8.0.2155/ReShade64.dll`).
- `LoadDLL` / `IncludeFile` lists: single ini with `[exe-stem]` sections, comma and/or repeated keys. At load the loader copies listed files/trees from the depot (`TUXGT_DEPOT`, `TUXGT_ADDONS` compat fallback, `[Init] DepotDir`, default `addons/` next to the ini) into the per-game base when missing or content differs (size fast path, sha256 when sizes match — libcrypto EVP, `NEEDED` libc + libcrypto — so the depot copy always wins). Unstaging: on `ok` runs the loader removes previously staged files the current config no longer references — the prior status file doubles as the manifest (exact recorded paths only; foreign/hand-placed files never match; tree per-file lines make the manifest precise; emptied tree roots are `rmdir`'d, which fails when non-empty). Generated files (logs, quirk-touched ini) are not staged files and stay; removing a game section orphans its base (delete `GamesDir/<stem>/` by hand). `IncludeFile` stages first (ini/trees exist before any load), then `LoadDLL` entries stage and `LoadLibraryW` in list order.
- Staging: copies verify (sha256 post-copy, size fast-path, 75ms backoff ×3, fail loud so the run skips prune+load); LoadDLL dests are re-verified vs the depot at load (a missing depot fails closed, `TUXGT_ESTALE` sentinel); stage and prune+status run under fcntl record-lock windows (~30s deadline, DllMain outside, prune skipped on timeout); prune keeps files created after run start (60s future clamp); late threads/gates spin on `load_wait` (stager-tid bypass for DllMain re-entrancy).
- `LoadDLL` token forms: `name` (depot file), `dest=src` (rename/subpath, e.g. proxy slots `d3d12.dll=ReShade/6.8.0.2155/ReShade64.dll`, `dxgi.dll=optiscaler/dxgi.dll`). `IncludeFile` adds `destdir/=srcdir/` recursive tree mirrors and bare files including `.addon64` — ReShade discovers those in the per-game base itself, so as far as the loader is concerned they are regular to-stage files. Only `*.dll` (case-insensitive) entries load. `..`, absolute, drive-letter and backslash tokens rejected; symlinks skipped. Status: `[IncludeFile]` then `[LoadDLL]` last (per-file `dest=result`, `dest=handle`; tree files listed per path, e.g. `OptiScaler/streamline/sl.dlss.dll=staged`; `[Load]` carries `Loaded=x/y`); the addon gates its read on `[LoadDLL]` being present.
- OptiScaler product payload is the official GitHub 7z (`docs/dev/app/plugin/instances.md`): app dests `OptiScaler.dll` → `dxgi.dll`, companions keep archive-relative dests. Loader never patches the ini. Abs `OptiDllPath` / `NvngxDlssPath` is `launch.staging-rewrites` (Later). Until that lands, official 0.9.x companions stage next to the `dxgi` dest in the per-game base. Custom/fork builds are a different instance id.
- OptiScaler caveats: its `LoadLibraryW` does not return in the headless probe — Proton stalls after its Vulkan state-tracker init log line; plain wine aborts on unimplemented `ntdll.NtMapUserPhysicalPagesScatter`. In-game it loads, so this is probe-environment-specific, not the loader path. Game-dir `nvngx_dlss.dll` override is not the product path.
- Depot trees are plural and injector-owned: `ReShade/<ver>/`, `NVStreamline/<ver>/`, `OptiScaler/…`, … Stock filenames kept as-shipped inside the tree; the per-game dest name picks the proxy slot. The user tarball does **not** seed these (`docs/dev/app/core/install.md`). ReShade and official OptiScaler arrive via app download. NVStreamline and first-party addons were dropped on reset (sources plus `make deploy-nvstreamline` / `make deploy-addons` are gone). No single global DLL. Host links are `tuxgt install`, not `make install`.
- Log redirect: proxy-named loads need none (DLL dir = base covers `ReShade.ini`/`ReShade.log`/effect runtimes; no `ReShade.ini` created, log lands in base). Stock-name loads get the quirk override above. Launcher script cannot do it (exe unknown until inject). Addon-own logs (bridge writes beside its DLL) do not follow base — accepted gap for now.
- Env: `TUXGT_GAMES` = parent of per-game dirs; `TUXGT_DEPOT` = versioned injector trees (`TUXGT_ADDONS` compat fallback). No `TUXGT_RESHADE`, no `TUXGT_VERSIONS`, no `RESHADE_HOME`. Loader debug to `stderr` + per-game `tuxgt-launcher.log` (appended at load, pid-tagged; helpers without a section never reach it).
- Never write game dir. Never write `external/`.

## Tree

- `src/launcher/*.c` + `tuxgt-launcher.h`: gates + per-game dir + override + `LoadLibraryW` once. Pure C, `gcc -shared -fPIC` (and `gcc -m32 -shared -fPIC` for the 32-bit companion).
- `src/launcher/tuxgt-launcher`: resolve self, find `.so`. Correlate prefix+exe via `$TUXGT_DATA/games/load-correlator.ini`, then read `games/<rel>/tux-protonfixes.conf` (same as the protonfixes hook). Missing → `preload_so` + `exec "$@"`; a session self-arms the trampoline (env + `WRAPPERS` + `.so`) at any `inject=` value (`inject=1` is hook-only): export session env, append-only `LD_PRELOAD` + `PRESSURE_VESSEL_FILESYSTEMS_RW`, exec `WRAPPERS` around `"$@"` (gamescope gets `--`). `preload_so` always appends the primary `TUXGT_LAUNCHER_SO` (or the 64-bit SO found next to the script) and, when present, the sibling ELF class in the same directory (`libtuxgt-launcher.so` ↔ `libtuxgt-launcher32.so`) so WoW64 wine (64-bit Unix process, 32-bit PE) still injects. Direct runs and session runs share that path. A session value that is not one shell word is double-quoted (`\`, `"`, `$`, and backticks escaped; newlines stay inside the quotes) so `=`, `;`, spaces, and newlines remain part of that assignment. The hook decodes the same quoting. A raw legacy value is the rest of the line, not a second statement.
- `tuxgt-launcher.ini`: `[Init] GamesDir + DepotDir`, `[Defaults] Type` seed (`dx12_64`). Env wins.
- `Makefile`: `preload` builds both `.so`s (`libtuxgt-launcher.so` + `libtuxgt-launcher32.so` via `gcc -m32` when available), `prepare`/`package`/`deploy` ship both; `app`/`app-trace`/`clean` as before. No `make install`. `prepare` fills `build/pkg/tuxgt` (no reshade-addons). Live prefix overlay (bin/lib/share): `make deploy` → `TUXGT_DATA` from `~/.config/tuxgt.conf`. Host PATH/desktop/boot conf: `tuxgt install`.

## Install tree (`make package` + `tuxgt install`)

- Layout: packaged `$PREFIX` is `bin/tuxgt`, `bin/tuxgt-launcher`, `lib/libtuxgt-launcher.so`, `mods/official/*.toml` (recipes only), empty `downloads/` / `config/` / `games/`, `share/` (`templates/*.toml`, `protonfixes/`, `icons/hicolor/*/apps/tuxgt.png` (9), `applications/`). No ReShade / NVStreamline / `.addon64` in the tarball. `tuxgt install` writes PATH symlinks, one KDE Games desktop, and `~/.config/tuxgt.conf`. `make deploy` overlays bin/lib/share and syncs `mods/official/*.toml` (gone ids drop toml + that payload dir) without touching `games/`, `downloads/`, `config/`, `mods/user/`, or kept official payloads.
- Status file: `tuxgt-launcher-status.ini` in the per-game base — `[Load]` (Type, Base, Result, Handle of last load, Loaded=x/y, Error), `[IncludeFile]` and `[LoadDLL]` (per-file `dest=staged|up-to-date|missing|failed`, `dest=handle`). Written on every load, success or failure, via temp + rename.

## Runtime

- Proton is the target (Steam default); plain wine is a fallback.
- Preload `.so` needs max `GLIBC_2.34` and `NEEDED` libc + `libcrypto.so.3`. proton-cachyos and Proton-GE both relax stock Proton injection restrictions.
- Known noise: helper exes (`winedevice`, `explorer`, `umu`, `tabtip`, `conhost`) arm gates (one `stderr` line each) but leave no per-game dirs. The opt-in section check gates `mkdir`, so no gate work needed.

## Limits

1. `AGENTS.md` allows the live prefix (`make deploy`) and `tuxgt install` host outputs (PATH symlinks, KDE desktop, boot conf). Not a general `$HOME` write grant.
2. `external/` read-only vs user-side depot trees: stock DLLs are used as-shipped, no rename/copy by the build; not vendoring.
3. Addon logs beside-DLL break per-game log purity for stock addons; fixable only in addons we own.
4. 32-bit DX9/DX10/DX11/DX12 plumbing (selection, `ReShade32.dll` arch-32 payload, `Type=dx9_32`/`dx9_64`/`dx10_32`/`dx10_64`/`dx11_32`/`dx11_64`/`dx12_32`/`dx12_64`, `libtuxgt-launcher32.so`, `DownloadUrl32` parsing) is in scope. The `-m32` SO has an i386 gate (`launch.32bit-in-game-gate` Exists). In-game DX9/DX10 proof is verified. Vulkan and XR remain explicitly out of scope.
